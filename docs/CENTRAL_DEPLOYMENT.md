# 중앙봇 연동 최종 준비

2026-09-11 운영 연동 가이드 기준. 과거 IP 및 도메인의 현재 연결 상태는 확인하지 않았다.

## 운영 서버 설정

`.env.example`을 참고해 운영 서버의 비공개 환경 설정에 입력한다. 키를 채팅, Git 또는 로그에 넣지 않는다.

| 설정 | 필요한 값 |
| --- | --- |
| `DECKOUT_CENTRAL_URL` | 중앙봇 Tailscale IP 또는 DNS와 포트를 포함한 URL |
| `DECKOUT_API_KEY` | deckout 전용 키: read, currency:grant, currency:deduct |
| `DECKOUT_INGRESS_SECRET` | 중앙봇과 Deckout 양쪽에 동일하게 설치하는 별도 공유 비밀 |
| `DECKOUT_CHANNEL_ID` | 전용 부모 채널 ID |
| `DECKOUT_DB` | 영속 디스크의 기존 DB 경로 |
| `DECKOUT_SKIP_CAPABILITY_CHECK` | 운영은 0 |
| `DECKOUT_ALLOW_UNAUTHENTICATED_LOCAL` | 운영은 0 |

관리자 화면을 사용하면 관리자 비밀번호와 서명 비밀도 서버에 설정한다. HTTPS에서는 보안 쿠키 설정을 유지한다.

## 중앙봇 설정

등록 이름 `deckout`, `channel`은 부모 채널, `service_url`은 **중앙봇에서 접근 가능한 Deckout 주소**로 설정하고 `route_threads: true`를 유지한다.
모든 `/event`와 `/shutdown` 요청에 `X-ARI-Minigame-Secret` 헤더를 붙인다. 배달 결과 및 스레드 삭제 콜백도 예외가 없다.
Deckout에서 중앙봇으로 보내는 요청은 별도 `X-API-Key`를 사용한다.
Tailscale은 양쪽 호스트가 연결되어야 하며 양방향 포트 접근이 필요하다. 같은 호스트가 아니면 loopback 주소로 서로 연결할 수 없다.

## 적용 순서

1. 기존 서비스 정지 후 SQLite DB 백업. 기존 DB에는 `bootstrap --force`를 실행하지 않는다.
2. 의존성 설치 및 기존 배포의 `python -m app.cli.upgrade_deck_refresh --db <기존-DB-경로>` 절차로 DB/콘텐츠 갱신. 이 명령의 기본 경로는 `deckout.db`이므로 운영 DB 경로를 반드시 명시한다.
3. 위 환경 설정을 적용하고 `python -m app.cli.check_central` 실행. 이 명령은 health/capabilities 조회만 수행한다.
4. Deckout 실행 후 `/healthz` 200 확인. 미준비·종료 중 또는 DB 접근 실패는 503이다.
5. 중앙봇 측에서 Deckout에 도달 가능한지 확인. 인증 없는 `/event`, `/shutdown`은 401이어야 한다. 비밀 미설정 시 운영 기동은 차단된다.
6. 지정 채널에서 `!덱아웃`을 실행해 개인 스레드 생성, 멘션, 버튼, 대상 선택, 이미지 분리, 콜백, 재시작 복구를 확인한다. 이 단계는 실제 플레이어 상태를 만든다.

기존 서비스에도 인증을 추가하므로 **중앙봇의 공유 헤더 설정을 함께 적용해야 한다**. 먼저 Deckout만 갱신하면 기존 요청이 401로 거절된다.

## 첫 지도 이미지 확인

런을 시작하면 부모 채널 응답은 개인 스레드로 안내한다. 이동 버튼은 부모 채널에
복제하지 않는다. 스레드 첫 메시지의 `지도 열기`를 누르면 PNG 지도와 이동 버튼이
함께 표시되어야 한다. 이어 이동 버튼을 눌러 전투 이미지와 조작 버튼을 확인한다.
스레드 생성 API에는 이미지 첨부 계약이 없으므로 첫 이미지는 이 버튼의 interaction
응답으로 전달한다. 생성 실패 시에는 재시도 안내만 표시하며 기존 런을 보존한다.

이미 열려 있던 스레드는 재시작 복구 후 스레드 안의 현재 버튼으로 확인한다.
기존 부모 채널 메시지에 남은 런 버튼은 스레드로 안내한다.

## 전투 이미지 순서와 메시지 갱신

전투는 조작 버튼이 있는 **한 메시지**를 계속 편집한다. 위에는 적·전투 기록,
아래에는 캐릭터·손패가 나오고, 조작은 그 아래에 남는다. 카드 대상 선택 중에도
두 그림을 함께 표시한다. 최근 행동 5줄은 같은 메시지 안에서 교체한다.

응답은 `edit` 하나에 PNG 두 장과 순서가 있는 이미지 `embeds` 두 개를 담는다.
이미지 URL은 각각 `attachment://deckout_situation.png`,
`attachment://deckout_turn.png`다. Discord의 첨부 이미지 embed 형식을 쓴다
([공식 파일 첨부 문서](https://docs.discord.com/developers/reference#uploading-files)).
Central은 첨부와 `embeds`를 함께 전달해야 한다. 전투 화면에서 다른 화면으로
넘어갈 때는 `embeds: []`로 이전 그림 참조를 제거한다.

전송 결과 콜백을 기다려 별도 전황 보드를 만들거나 고치지 않으므로, 콜백이
늦어도 전황 메시지를 반복 생성하지 않는다. 업데이트 전에 게시된 전황 메시지는
그대로 남는다. 기존 스레드에서 `!덱아웃`을 한 번 입력해 새 형식의 현재 화면을
받은 뒤 해당 메시지의 조작을 사용한다. 실제 Discord에서 위아래 배치, 사진을
눌렀을 때 확대, 카드 사용 후 같은 메시지가 갱신되는지를 확인한다.

이 화면 배치 변경만 적용할 때는 콘텐츠를 다시 발행할 필요가 없다. 서버를
멈추고 기존 DB를 백업한 뒤 코드를 갱신하고 같은 DB 경로로 재실행한다.

## 스레드 화면 복구와 오류 구분

- 개인 스레드 **안에서** `!덱아웃` 또는 `!덱아웃 시작`을 입력하면 현재 저장된
  지도/전투 이미지와 버튼을 일반 메시지로 다시 받는다. 스레드 멤버에게 보이며,
  게임 조작은 계속 런 소유자만 할 수 있다. 부모 채널에서는 해당 스레드로 안내한다.
- 출석 버튼은 소유자 ID를 포함한다. 예전 출석 버튼을 미가입자가 눌러도
  계정을 자동 생성하거나 보상을 지급하지 않고 가입 안내를 반환한다.
- **운영 로그의 `messages/edit` 409 원인(2026-09-29 확인):** Deckout은 버튼을
  누를 때마다 로컬 `presentation_revision`(CAS 카운터)을 올리는데, 그 값을
  Central의 편집 revision으로도 보내고 있었다. 클릭 응답(응답 경로 `edit`)은
  Central의 값을 올리지 않으므로, 첫 클릭 이후의 모든 OOB 편집(런 종료 화면,
  재시작 복구)이 `stale_revision`으로 거절됐다. 스키마 v11에서
  `runs.central_revision`을 따로 두어 해결했다. 새 스레드 바인딩은 0에서
  시작한다고 가정한다(생성 응답이 값을 주면 그 값을 쓴다) — 운영에서 409가
  계속되면 Central 관리자에게 바인딩 초기 revision을 확인한다.
- 로그에는 알려진 `code`와 `gen`, `central_rev`만 남긴다. 응답 원문·헤더·키를
  출력하지 않는다. `code=unknown`이면 Central 관리자가 거절 사유를 확인한다.
- 409나 실패 응답에서 화면 번호를 올리지 않는다. DB 초기화, 런 삭제,
  새 세대 강제 생성으로 충돌을 감추지 않는다.

## 아직 필요한 정보

중앙봇 URL(포트 포함), Deckout 실행 호스트와 접근 주소/포트, 부모 채널 확인, Tailscale 양방향 연결 상태, 운영 호스트 접근 방법.
API 키와 공유 비밀은 운영 호스트에 설치한 후 설정 완료 여부만 확인한다. 현재 작업 공간의 프로세스는 상시 운영 서버를 대신하지 않는다.
